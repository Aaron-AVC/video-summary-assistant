将 ZIP 解压到克隆内临时目录后与 `build/chrome-mv3-prod` 逐文件比对：

**关于哈希可复现性（重要，已实测修正）**：本轮多次构建观察到 **`manifest.json` 的 SHA-256 并非每次稳定**。相同源码、相同提交树连续两次 `bun run build` 得到：

- `179601c4b18495c476475d3c686c1abe0faa1b3295ad5149499f9c5adac8ae47`
- `fbb4b4b5196cc38c06b7505fdb446c8b8ac35e11b19f5824eb3a16bf524ea4fb`

逐字节比对后确认唯一差异是 `content_scripts` 数组中 YouTube 与 Bilibili 两个条目的**顺序互换**（内容、`permissions`、`host_permissions`、`version` 等全部相同）。这是打包器对条目顺序不保证稳定所致，不涉及任何权限或功能差异。

ZIP 的 SHA-256 同样每次 `bun run package` 都变化（归档条目携带打包时刻的 mtime，且随 manifest 顺序变化）。本轮多次打包分别得到 `2366b6ee…`、`f9841fa4…`、`ca9a01cb…`、`2ebc32b9…`、`76d4b15c…`、`ec630cbd…`、`c6e22ccd…`、`497f0f24…`、`d24063f4…`，每次解压后都与当时的构建目录逐字节一致。

**结论**：产物哈希只对应当次构建，不能作为跨构建或跨机器的可复现性证据。本轮核验的是同次打包产物与构建目录的一致性及 Manifest 语义字段，而非跨构建可复现性：每次打包后的 ZIP 解压内容均与该次构建目录逐字节一致；不同打包结果的 ZIP 哈希存在变化，原记录将其归因于归档条目的打包时刻 mtime 及 Manifest 顺序变化。本轮核对的 `version`、`permissions`、`host_permissions`、`optional_host_permissions`、`manifest_version`、`side_panel` 等语义字段符合预期。以上证据不证明独立重复构建会产生相同的字节级输出。本条记录的是打包器产物差异，不构成已证实的产品功能缺陷，也未据此修改代码或配置。

3. **adapter 失败 fallback 的 canonicalUrl**：`current-video.ts` 在 adapter 失败时 fallback 为 `url.href`，但同路径 `isReady: false`，Knowledge 与 Markdown export 均要求 `isReady`，不 ready 时不落库也不导出。

5. **`DATABASE_VERSION` 推导值**：由 `MIGRATION_BLOCKS` 取最大值得到（实际为 6），除定义外全仓无引用，属恒等推导。
