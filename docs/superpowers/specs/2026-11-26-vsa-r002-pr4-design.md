# VSA-R002-PR4 Release Packaging and Compliance Gate

## Intent

Provide one reviewed packaging path that turns the fixed R002-B production artifact and freshly derived third-party notice plan into a verified Chrome MV3 ZIP. The internal package remains usable while project-rights approval is on hold; the ordinary `package` command must refuse to produce a formal package until an authentic future release qualification exists.

## Goals

- Reuse R002-B's fixed build identity, Parcel graph, candidate ledger, distribution scope, notice generator, and Chromium Artifact Gate.
- Generate and validate an internal ZIP containing exactly the 14 accepted production files, the 31 freshly derived notice files, and one internal/HOLD marker.
- Bind source, build-input/artifact, distribution, package type, qualification, and ZIP identities in an external record.
- Refuse modified inputs, missing or extra archive files, altered legal bytes, unsafe ZIP names, duplicate/case-colliding names, links, malformed archives, stale notice plans, and changed external identity records.
- Keep the real project-rights state as `HOLD`, preserve PR-5 as the authority/policy decision point, and make no upload or publication call.
- Preserve the historic build evidence byte-for-byte.

## Non-goals

- No product behavior, business source, dependency version, database schema, manifest permission, icon, extension version, or production build change.
- No project root `LICENSE`, project-rights approval, or formal release authorization.
- No publishing, uploading, GitHub remote write, PR, merge, or release action.
- No general-purpose supply-chain attestation framework or automatic legal review of future dependencies.

## Approaches

1. **Keep Plasmo's `package` command.** Its installed implementation zips a broad build directory and excludes source maps, but it does not derive the accepted notice plan, enforce the project-rights hold, or verify the finished archive against R002-B identities. It cannot serve as the compliance gate.
2. **Use a single TypeScript package coordinator with the locked Plasmo `fflate` implementation.** This reuses the exact fixed production artifact and notice APIs, stages only explicit expected files, and validates the real ZIP before publishing its output directory. This is the selected approach because `plasmo@0.90.5` already pins `fflate@0.8.2`; it adds no dependency and keeps the build lock unchanged. A bounded central-directory metadata inspection rejects ZIP entry aliases and non-regular file types; `fflate` performs compression and decompression.
3. **Use an operating-system ZIP command.** This would create platform-specific behavior and make archive metadata and byte checks depend on local tools, so it is not selected.

## Architecture

- `scripts/lib/release-package.ts` owns package planning, staging, ZIP metadata checks, byte-for-byte archive verification, source/build/distribution identity records, privacy checks, and no-overwrite publication.
- `scripts/release-package.ts` owns strict CLI parsing and delegates to the shared library. `package:internal`, `package`, and `verify:package` use the same plan and archive verifier. The release mode is permanently tied to the current derived qualification and has no user-supplied approval or bypass flag.
- `scripts/licensing/r002-b-candidate.ts` permits only these exact packaging-script changes while continuing to compare all other package fields, all other scripts, dependencies, overrides, and `bun.lock` against fixed build evidence:
  - `package`: `bun scripts/release-package.ts release`
  - `package:internal`: `bun scripts/release-package.ts internal`
  - `verify:package`: `bun scripts/release-package.ts verify`
- The product file set comes from the fixed build's exact artifact identity, not an assumed universal file count. The notice file set comes from `loadCandidate()`, `deriveScope()`, and `noticeFiles(..., true)` on every run. A generated internal marker is the only additional file.
- Staging is created in an isolated, fresh directory. Inputs and staging are checked for symlinks, junctions, special files, path escape, and unexpected entries. The ZIP is written and independently verified before a same-filesystem no-overwrite directory rename exposes the package and its external identity record.
- The ZIP contains no self-hash. Its SHA-256 and complete file inventory are stored in the adjacent external identity JSON and rederived by `verify:package`.

## Identity and status model

- **Source identity:** final Git commit and Tree; for a dirty pre-commit validation, also the captured Git diff and untracked-file identity. The final review package is generated from the committed candidate.
- **Build identity:** original build-source commit/Tree, fixed evidence SHA-256, locked build-relevant package fields, `bun.lock`, tool versions, and all 14 product-file hashes and byte lengths. Packaging scripts are recorded separately and are the only permitted package-manifest delta.
- **Distribution identity:** version, Chrome MV3 target, package type, derived scope and ledger hashes, notice manifest and file inventory, third-party status, project-rights status, release qualification, archive SHA-256, and archive length.
- Current derived state remains `THIRD_PARTY_NOTICES_COMPLETE_RELEASE_HOLD`, `MATERIALS_VERIFIED_FOR_REVIEWED_SCOPE`, zero third-party blockers, one project-rights blocker, and `releaseApproved: false`.

## ZIP policy

- The archive root contains `manifest.json` and the other exact production files.
- Include all notice-plan outputs byte-for-byte and a clearly named `INTERNAL_HOLD.txt`.
- Accept only the expected regular files; reject duplicate entries, case aliases, absolute paths, `..`, backslashes, drive/ADS syntax, links, directories, special file types, encryption, unsupported compression, ZIP64, malformed local/central records, and trailing bytes.
- Compare decompressed bytes and lengths to the newly derived expected map. Verify the root Manifest V3 manifest and its product version.
- Use a fresh ignored `dist/` output location. Refuse existing destinations; publish a completed package directory atomically only after ZIP, identity, and privacy validation pass.
- The regular `package` command returns non-zero under the actual hold before creating formal output. It has no force, ignore-rights, environment override, or manual approval argument.

## Chrome Web Store references

Checked on 2026-11-26:

- [Prepare your extension](https://developer.chrome.com/docs/webstore/prepare) says the uploaded ZIP contains the extension files and `manifest.json` must be at the ZIP root.
- [Use the Chrome Web Store API](https://developer.chrome.com/docs/webstore/using-api) states a maximum package size of 2 GB. The gate uses the conservative decimal ceiling of 2,000,000,000 bytes.
- The API documentation describes upload and publish as separate authorized actions; PR4 implements neither action.

## Validation

- Use TDD for package-manifest equivalence, path and ZIP metadata rejection, exact file identity, HOLD behavior, external identity tampering, staging cleanup, no-overwrite behavior, and a real generated/extracted ZIP.
- Run historic and current R002-B candidate/notice checks, license ledger validation, focused package tests, the full Bun test suite, TypeScript, `git diff --check`, the package CLI, and the real Chromium Artifact Gate against the extracted package.
- Retain exact logs and exit codes. Reuse the accepted production artifact only after the fixed candidate validator confirms all 14 files.
- Scan the final archive and targeted checked-in R002-B validation/build logs for local paths and secret-like data. Report false positives and any environment paths separately from actual credentials.
- Build and verify the internal archive after the final local commit so its external source identity points to the final committed candidate.

## PR-5 connection

PR-5 may provide a separately reviewed, rights-holder-authorized release qualification input. PR4's formal path must validate that future input through an explicit code-owned contract. No file in this change can approve the project, and no mock approval fixture is read by the real CLI.
